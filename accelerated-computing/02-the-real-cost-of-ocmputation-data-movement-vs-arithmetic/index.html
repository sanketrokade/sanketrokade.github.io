The Real Cost of Computation: Data Movement vs Arithmetic

Accelerated Computing — From First Principles (Part 2)

In the previous article, we saw why simply making CPUs faster stopped working. Clock speeds hit physical limits, complexity exploded, and performance gains slowed to a crawl.

But that still leaves an uncomfortable question unanswered.

Modern processors can execute billions of arithmetic operations per second. Multiplications, additions, fused operations — all of them are astonishingly fast. If arithmetic is so cheap, why do real programs still feel slow?

The answer is unintuitive at first, but once you see it, you cannot unsee it:

Most programs are not limited by computation. They are limited by data movement.

Understanding this single idea is essential to understanding accelerated computing.

1. What Do We Mean by “Computation”?

When people talk about computation, they usually imagine math:

  • Adding numbers
  • Multiplying matrices
  • Evaluating equations

But from the hardware’s point of view, a program is made of three very different kinds of work:

  • Arithmetic operations — Add, multiply, compare, shift.
  • Data movement — Load data from memory, store results, move values between different parts of the system.
  • Control and bookkeeping — Branching, checking conditions, managing instruction flow.

Only the first category is “math”. And it turns out to be the cheapest part.

2. A Computer Is Not One Place — It Is a Distance Problem

A useful way to think about a computer is not as a single machine, but as a hierarchy of locations. Data can live in:

  • CPU registers (right next to the execution units)
  • Small, fast caches
  • Larger, slower caches
  • Main memory (RAM)
  • Storage (SSD, disk)

The farther the data is from where computation happens:

  • The longer it takes to access
  • The more energy it costs to move

This distance is not metaphorical. It is physical. Signals have to travel through wires, across chip boundaries, through memory controllers. Physics does not care how clever our software is.

3. A Simple Thought Experiment

Consider two situations.

Case A

You want to add two numbers that are already in CPU registers. The processor:

  • Fetches the instruction
  • Performs the addition
  • Produces the result

This takes only a few clock cycles.

Case B

You want to add two numbers that live in main memory. Now the processor must:

  • Request the data from memory
  • Wait while it travels across the memory bus
  • Load it into caches
  • Move it into registers
  • Finally perform the same addition

The arithmetic operation is identical in both cases. The cost difference comes entirely from moving the data.

In many real programs, the arithmetic is fast enough that it barely matters. What dominates execution time is waiting for data to arrive.

4. Why Memory Is So Much Slower Than Computation

One might ask: If arithmetic got so fast, why didn’t memory keep up?

Because memory faces a different set of constraints:

  • Memory cells are optimized for density, not speed.
  • Long wires introduce delay and energy loss.
  • Increasing memory bandwidth consumes enormous power.
  • Fast memory is expensive and physically limited.

As processors improved, arithmetic speed increased rapidly. Memory speed improved too — but much more slowly.

This created a widening gap between:

  • How fast we can compute
  • How fast we can feed data to the computation

This gap is known as the memory wall.

5. The Hidden Cost: Energy, Not Just Time

Latency is only part of the story.

Moving data costs energy — often far more than doing arithmetic.

Flipping a few bits inside a register is cheap. Sending those same bits across a chip, or off the chip to memory, burns orders of magnitude more energy.

This matters because:

  • Energy turns into heat
  • Heat limits how much hardware can be active
  • Power limits cap overall performance

Many performance limits today are not about speed — they are about staying within a power budget.

6. Why CPUs Are So Complicated

Modern CPUs look incredibly complex:

  • Multiple cache levels
  • Out-of-order execution
  • Speculative loads
  • Branch prediction

It is tempting to think all this exists to compute faster.

In reality, much of it exists to hide memory latency.

CPUs try to:

  • Guess what data you will need next
  • Fetch it early
  • Keep execution units busy while waiting

Sometimes this works beautifully. Sometimes it fails, and the processor stalls — doing almost nothing while waiting for data.

As workloads grew larger and more data-intensive, hiding memory latency became harder and harder.

7. The Key Insight That Changes Everything

At this point, a fundamental realization emerges:

Performance is dominated by how efficiently data moves, not by how fast arithmetic executes.

This has profound consequences.

If arithmetic is cheap and data movement is expensive, then:

  • Doing more math per byte of data is good
  • Moving less data is even better
  • Architectures that minimize data movement win

This is not an optimization trick. It is a first-principles constraint.
